03 Problem

When it compresses, the wrong things disappear.

What gets lost first

  • Hard rules ("never leak model names to users")
  • Cross-session projects ("TRCE funnel state")
  • Communication style ("terse, British slang, options-then-pick")
  • Stable personal facts ("works nights, sleeps 1:30pm")
  • Tool quirks learned the hard way ("beepbo auth.py line numbers")

What survives

  • Recent one-off tasks
  • Transient build details
  • Session-specific debugging
  • The very thing you needed to preserve gets compressed away
04 Diagnosis

One file is doing two jobs.

High-signal

Hard preferences, communication rules, project structure, tool quirks. Changes rarely. Must never lose.

Estimated size: ~2,000 chars

Update cadence: manual, after proven

Session-derived

One-off facts, build state, "remember when I asked X", debugging breadcrumbs. High churn, low urgency.

Estimated size: unbounded

Update cadence: every turn

The 50K budget can't tell the two apart. Compression treats them identically.

08 Mechanism

How a fact flows through the tiers.

# 1. Conversation turn ends
Henry saves: "TRCE funnel: view_landing → view_signup → ... → click_upgrade"
↓
# 2. Tierer classifies (rule-based, not LLM)
keyword match: "funnel", "TRCE" → warm
new fact count: 1 → do not auto-promote
↓
# 3. Stored in warm tier with tags
{ tier: warm, tags: [trce, analytics], chars: 287 }
↓
# 4. Future query: "what's TRCE's funnel state?"
tag match: ["trce", "funnel"] → inject this entry
↓
# 5. Nightly consolidator (optional)
if mentions ≥ 10 in 30 days → suggest promotion to hot
09 Component

The nightly consolidator.

Runs once a day. Reads everything. Suggests changes. Never auto-deletes.

  • Merges duplicate facts ("Nick works nights" + "Nick is nocturnal" → 1 entry)
  • Promotes warm → hot when a fact appears in 10+ conversations
  • Demotes hot → warm when unused for 90 days OR contradicted
  • Flags unused tier-1 rules to the user: "still true?"
  • Detects contradiction: "you said X on Sep 1, X̄ on Sep 8"
  • Reports size impact: "saved 4,200 chars this run"
  • Backs up pre-consolidation MEMORY.md → ~/.hermes/memory-backups/
  • Hooks into existing MemPalace dailysync — no new cron needed
10 Interface

One CLI. Zero magic.

# Inspect what's loaded right now
hermes memory status
  hot: 1,847 chars · 14 rules
  warm: 7,403 chars · 38 facts
  cold: 12,944 vectors · 6,402 entries
  next consolidator run: 14h 22m

# Search across all tiers
hermes memory search "TRCE funnel"
  warm · 287 chars · "TRCE funnel: view_landing → view_signup → ... → click_upgrade"

# Promote a fact (warm → hot, requires user confirmation)
hermes memory promote "always use British slang in intro copy"
  → promoted to hot, 142 chars added

# Run consolidator manually
hermes memory consolidate --dry-run
  would merge 7 duplicate pairs (1,240 chars)
  would suggest 2 promotions to hot
  would flag 1 contradiction (your review required)

13 Verdict

Honest assessment.

Worth building

For the Hermes community: massive. Every user hits the 50K wall. A drop-in solution is a genuine product unlock.

For your positioning: if Hermes is ever more than a personal tool, memory infrastructure is real differentiation. Most agent frameworks treat memory as "stick it in JSON and pray."

For you personally: smaller but real. Stops the compression cliff. Lower per-turn token cost.

Worth knowing

Your current memory is already excellent. Months of careful curation. The harness would validate and extend it, not replace it.

Retrieval adds latency. Embedding lookups are fast (~5-20ms) but non-zero. Worth it for the cost savings.

Risk: a buggy consolidator that mis-merges facts is worse than the compression wall. Needs careful rollback design.
